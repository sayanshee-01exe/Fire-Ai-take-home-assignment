# Project A: results

Project A computes Indian income tax for salaried residents under both regimes. It has three implementations
and a plain-language front end:

- **Hand-coded:** a rules engine with exact fractions and one params file per year.
- **LLM at query time:** gemini-3.1-flash-lite is given the rules text and computes each answer.
- **LLM-compiled:** gemini-3.5-flash-lite writes the engine as code once, a reviewer edits it, and it runs in a sandbox.
- **Parser:** gemini-3.5-flash-lite turns free text into the engine's input. It extracts only; code decides.

A local demo UI in [ui/](ui/) calls the same parser pipeline and hand-coded engine as the CLI and computes nothing
itself (see [ui/README.md](ui/README.md)).

Every number below is taken from one of these sources:
- [RESULTS_TABLES.md](RESULTS_TABLES.md) ("RT §n"), which is generated by `python3 -m project_a.eval.compare` from the recorded results files;
- [project_a/task5/TASK5_LOG.md](project_a/task5/TASK5_LOG.md) ("TASK5_LOG");
- [project_a/eval/MEASUREMENT_LOG.md](project_a/eval/MEASUREMENT_LOG.md);
- the files under `project_a/eval/results/` and `project_a/compiler/compiled/`.

Where something was not measured, it says so.

Splits:
- **dev** cases could be looked at while building.
- **heldout** cases were run once at the end.
- **official** rows were checked by hand on the Income Tax Department's Advanced calculator: 30 rows for FY 2024-25 and 12 for FY 2025-26.
- Some heldout cases are also official rows: 25 in FY 2024-25 and 7 in FY 2025-26. Results are shown with and without them.

## 1. Comparison of the three implementations

- **strict raw:** the compiler's output under the production allow-list. A rejected artifact answers nothing.
- **diagnostic raw:** the same code with only the one-function rule relaxed.

### 1.3 Traceability

There are three levels:
- **(a)** every step carries a clause ID, and the reported amounts appear in the trace;
- **(b)** every clause ID exists in that year's rules text;
- **(c)** every step amount equals an independent recomputation (strict to 0.01 rupee, and also within Rs 1).

## 2. Parser (plain language to engine input)

The parser ran on the 50-query NL set: 15 dev and 35 heldout, in English, Hinglish and mixed. It used
gemini-3.5-flash-lite with prompt v1. Source: RT §3 and §4. The LLM calls were recorded on 2026-11-20
(`results/nl_v1_dev_auto_20261120T184637Z.json`, `results/nl_v1_heldout_auto_20261120T195740Z.json`,
`results/determinism_parser_20261120T221955Z.json`). The figures below are those same recorded LLM outputs replayed
on 2026-11-21 through the current code (`*_replay_20261121T064130Z.json`), after two code fixes: FY 2025-26 queries
are now computed, and a zero amount's period no longer triggers a question.

| Split | Behaviour correct | Compute fields exact | End-to-end tax correct | False computes | Parse errors |
|---|---|---|---|---|---|
| dev | 14/15 | 117/117 | 9/9 | 1/6 | 0 |
| heldout | 32/35 (91.4%) | 273/273 | 21/21 | 1/14 | 0 |

Heldout behaviour by expected outcome:
- compute 21/21;
- ask 6/7;
- unsupported 5/5;
- law-change 0/2.

The frozen set labels its three FY 2025-26 queries "law-change": they were written when those rules were not
loaded. The pipeline now computes FY 2025-26, so scored against the frozen labels all three count as wrong:
- NL-49 (dev) and NL-50 (heldout) compute with the FY 2025-26 engine. They are the two false computes, and both
  answers match the oracle (old Rs 1,87,200 / new Rs 0, and old Rs 3,51,000 / new Rs 1,50,800);
- NL-48 asks for the age.

There are no other false computes. Before the routing fix, the recorded runs scored dev 15/15 and heldout 34/35,
with 0 false computes.

The one other miss is NL-36: CTC of 18 lakh "including employer PF". It should have asked about gross salary; the
model tagged employer NPS, so the parser refused. That is an over-refusal, the safe direction.

Determinism (10 dev queries × 10 repeats, all 100 runs done):
- the extraction was identical on 4/10 queries;
- the outcome was identical on 10/10;
- the final engine input was identical on 10/10.

With the code as recorded it was 9/10 for both. The exception was NL-14. The user wrote "rent nahi deta" (rent 0),
and the model reported that zero rent's period as "annual" on 5 runs and "unknown" on 5. Code asked a question
whenever a period was unknown, even for a zero amount, so the outcome flipped between ask and compute. Code now
treats a zero amount as having no period to ask about. The model's output still varies, but the outcome no longer
does.

Latency (LLM attempts per query): mean 2.9 s, p50 2.0 s, p95 3.4 s, max 39.5 s (50 samples). Notional cost:
$1.61 per 1,000 queries (3,194 prompt + 259 output tokens per query).

## 4. Limits and honesty

1. **Query-time determinism finished 9 of 20 cases.** The free-tier daily quota for gemini-3.1-flash-lite returned
   HTTP 429 after 503 requests that day. The other runs ended as follows:
   - slab_boundary-36 has 4 of its 10 runs;
   - 10 cases were not run;
   - repeat 0 of each case was replayed from earlier recordings, not called again.

   Finishing needs about 106 more calls after the quota resets; the 95 recorded runs replay from the cache.
   "Deterministic but wrong" rests on 9 cases, plus the 4 runs of the tenth.
2. **The compiled-code review was done by the AI assistant, not by an independent person.** For FY 2025-26 it took
   116 s (TASK5_LOG c3). The FY 2024-25 review time was not recorded.
3. **The NL queries and the topic map were written with AI help**, by the same assistant that built the parser.
   The heldout parser results (32/35 against the frozen labels) are therefore not fully blind. The NL-14 and
   FY 2025-26 fixes were made after the heldout run, and the heldout replay is a second look at that split.
4. **The engine, the oracle and the golden cases were all written with the same AI assistant.** Their independence
   is structural, not authorial:
   - the oracle imports only `decimal` and `fractions` and is written in its own differential form;
   - it caught 7/7 wrong parameter sets;
   - the mutation check caught 14 of 15 mutants, the 15th being equivalent;
   - engine and oracle agree with the official calculator on 120/120 FY 2024-25 fields and 48/48 FY 2025-26 fields.

   An error shared by the rules text, the engine and the oracle would only be caught by the official rows.
5. **Official rows overlap heldout:** 25 of 156 FY 2024-25 heldout cases and 7 of 129 FY 2025-26. RT §1 shows
   heldout with and without them.
6. **The oracle exposes no step values.** Traceability level (c) therefore recomputes each step from the rules text,
   using the oracle's helper functions for the tax chain (slab differentials, surcharge and its relief, the new-regime
   rebate table). So (c) is independent of the implementation under test, but not of the oracle's formulas.
7. **Deduction caps were carried from the rules text and never confirmed on the official calculator.** No official
   row in either year enters an amount above a cap:
   - 80C 1.5 lakh, 80CCD(1B) 50,000 and 24(b) 2 lakh are never exceeded;
   - the 80D amounts are at most at their caps and are entered as one combined field;
   - the calculator does not check the HRA formula, because the exemption is entered as an amount.

   See TASK5_LOG risk R3 and README "What the official calculator does and does not verify".
8. **The standard-deduction trace label.** The 4 reviewed FY 2024-25 answers that miss (c) by more than Rs 1 are
   degenerate-01 to -04 (gross salary 0, 1, 40,000 and 50,000). They record C-STD-NEW as 75,000, but the deduction
   cannot exceed the salary. The tax is still correct. The checker caps it, while RULES_FY2024_25.md states
   "limited to salary" for C-STD-OLD and not for C-STD-NEW, so the gap is in the rules text. The other strict (c)
   misses are paise in intermediate steps, and within Rs 1 they pass.
9. **macOS memory limit.** macOS refuses memory rlimits, so on macOS the sandbox enforces memory with a parent-side
   watchdog: it reads the worker's virtual size with `/bin/ps` while it waits, about every 50 ms, and kills the worker
   if it grows past the limit. This is a poll, not a hard OS limit, and it was not stress-tested. On Linux, RLIMIT_AS
   applies.
10. **Other limits:**
    - Costs are notional list prices; the free tier cost $0.
    - Latency was measured on one machine and one network on 2026-11-20.
    - Three results files were run by the author from a terminal with the same harness and cache: the query-time
      FY 2024-25 dev and heldout runs, and the parser heldout run. Latency and cost include them.
    - Usage logs show 8 requests to gemini-3-flash-preview that no results file corresponds to.
    - The query engine was measured with one model at temperature 0. Other models were not compared.
    - The hand-coded engine's heldout result is not blind: pytest checks it on every golden case, heldout included.
      Heldout was blind only for the LLM implementations and the compiled-code reviews.
11. **Parser gaps, not measured.**
    - The parser has no tag for a let-out or second property. Home-loan interest is always treated as
      a self-occupied house's (C-24B, capped at Rs 2 lakh in the old regime), unless the LLM tags it
      "other unsupported".
    - A very vague query can end at the 5-round cap on clarifying questions (the CLI's `--interactive`
      and the UI). It then stops with status "ask" and no tax.
12. **The demo UI's breakup shows only the engine's clause trace.**
    - The trace has no HRA three-amount split (HRA received, 40%/50% of basic, rent minus 10% of basic)
      and no per-slab lines, so the UI shows them as "not in trace" rather than recomputing them.
    - The C-288A and C-288B roundings have no trace step. The UI shows them as "derived" lines, the gap
      between two trace steps.

## 5. Final design

**Principle: the LLM handles language and code handles tax.** Each component is labelled **RULE** (deterministic
code), **LLM**, or **HYBRID** (the LLM reports what it read and code decides). Anything the code does not do is
marked **proposed, not implemented**. Figures are from §1–§4.

**Free text to structured input: HYBRID.** The LLM reports only what the user wrote: each amount as a number,
a scale and a period, with the quoted phrase, plus tags from closed lists. Code converts amounts to rupees, maps
the city, checks the required facts and decides the outcome: compute, ask or unsupported. On heldout, 273/273
compute fields were exact and behaviour was 32/35 against the frozen labels (§2). Over 10 repeats the extraction
varied (identical 4/10) but the outcome did not (10/10). Code therefore owns the outcome.

The CLI (`python3 -m project_a.cli`) prints the extraction, the code's decisions and the status, then on
"compute" the normalised input and both taxes at once, noting when only the standard deduction was assumed.
Showing the parsed inputs for the user to confirm before computing is **proposed, not implemented**:
`--interactive` only answers clarifying questions.

**Missing or ambiguous information: RULE.** Code checks the required facts: age, year and gross salary; the
city, HRA received and basic salary when rent is paid; the interest part of an EMI; and the parents' age when it
changes the 80D cap. It never defaults a missing age or year. Code decides which facts to ask about. The wording
comes from the extraction call itself:
- if the LLM flagged the same tag (and field), its question is shown as written. The prompt asks for the user's
  language; code does not check the text;
- otherwise code uses a fixed English template (`TEMPLATES` in `project_a/parser/normalise.py`).

Each question records which was used (`source`: llm or template). Answers are applied by code with no further LLM
call, for up to 5 rounds. Four tags that code cannot check from the text (CTC versus gross, conflicting amounts,
a missing amount, other) rely on the LLM's flag. That is the weakest link: 6/7 heldout asks were right.

**Out-of-scope detection: HYBRID.** The LLM tags from a closed list: employer NPS, HRA in two cities, capital
gains, business income, non-resident, foreign income, ESOPs, other. Code refuses on any tag and never calls the
engine. Heldout: 5/5 refused, plus one over-refusal (NL-36), which is the safe direction.

**Tax calculation and regime comparison: RULE.** A hand-coded engine with exact fractions and one params file
per financial year. It is rupee-exact on every dev, heldout and official case in both years (§1.1), identical over
10 repeats on 381/381, and takes 33 µs a call at no cost. FY 2025-26 needed zero engine lines. The lower
tax wins; a tie goes to the new regime.

**Explanation and traceability: RULE.** The engine writes the trace, and every amount carries a clause ID from
that year's rules text. Its traces pass all three levels on 381/381 answers. The CLI prints the two regimes'
totals and the engine's one-line reason; the demo UI shows the trace as a breakup (§4 item 12). Having an LLM
reword the explanation, with a check that every number in its text matches the trace and the text dropped
otherwise, is **proposed, not implemented**: no code calls an LLM after the engine.

**Arithmetic by an LLM at query time: NOT USED.** Tax exact on 16.0% of FY 2024-25 heldout cases, silently
wrong on 143/173 FY 2025-26 answers, deterministic but wrong, and trace level (c) on 31/381 answers (§1, §3).

**New Budget: HYBRID.** An LLM compiles a candidate engine from the new rules text, and a reviewer edits it
against the text. For FY 2025-26 the reviewer was the AI assistant, not a person (§4 item 2). Time to apply is
measured from the start of the first compile to the end of the review: 3 min 10 s (20:42:49–20:45:59 UTC,
TASK5_LOG). That is compiles 33 s, checks 25 s and review 116 s, plus 16 s between steps; the heldout run ended
at 20:46:35. None of the three raw outputs was shippable (§3, "What broke").

The allow-list and the year guard run on every call of the compiled engine. pytest checks the FY 2025-26
reviewed artifact on the official rows, and the oracle suite is run with the eval harness. A release gate that
blocks an artifact until all of these pass is **proposed, not implemented**. The CLI and the parser pipeline use
only the hand-coded engine. When a change fits the params file, as FY 2025-26 did, editing it is quicker
(46 s, §3). Compiling pays off when the structure of the law changes.

**Keeping it correct through the next Budget:**
- one params file per financial year;
- an oracle written from the official text and kept independent: it caught 7/7 wrong FY 2025-26 parameter sets;
- 10 to 12 official-calculator rows around every changed threshold (FY 2025-26: 12 rows, 48/48 fields);
- mutation checks: 14 of 15 mutants caught, the 15th equivalent;
- a loud year guard, so an unknown year raises an error (without it, 136/173 answers were silently wrong);
- monitoring that samples production inputs, recomputes them with the oracle and alerts on any difference:
  **proposed, not implemented**.

**At 100,000 users.** Only the parser costs money per query: $1.61 per 1,000 notional, $161 per 100,000
queries. Queries per user were not measured. Response time is the parser's: mean 2.9 s, p95 3.4 s, worst 39.5 s.
Throughput is limited by quota (§4 item 1; the parser model's daily limit was not measured) and by the
client's default throttle of 8 requests per minute (`LLM_RPM`).

Changes for that scale, all **proposed, not implemented**:
- the paid tier;
- a form path that sends structured input straight to the engine with no LLM call;
- caching by normalised query text. The current cache matches exact prompts, and its hit rate on real traffic
  is unknown;
- batch requests for non-interactive work.
