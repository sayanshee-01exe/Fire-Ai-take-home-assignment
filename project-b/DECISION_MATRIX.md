# Decision matrix

One row per component or check, marked rule, statistical, LLM or hybrid, with the measurement
that justifies it and the trade-offs in auditability, determinism and maintenance. Generated by
`python -m project_b.report` from `project_b/results/`; the choices come from
`project_b/pipeline.py` (`plan_from_summary`), so the matrix and the pipeline cannot disagree.

## Project B - data-quality checks

**Decision rule** (fixed before any benchmark result existed): A rule / statistical detector qualifies when its false alarms stay within 0.2% of clean rows (row-level problems) or 10% of clean batches (batch-level problems). Among those, the highest detection wins; within 2 points the rule wins (cheaper, deterministic, self-explaining). For problems c, f, l both run when both qualify (they see different evidence). An LLM is added only as a confirmer, and only when the chosen detector's precision at the injection rate is below 0.90 and, on the very rows the LLM reviewed, it raises fewer false alarms while catching at least as much (within 2 points). A detector counts as measured only with at least 10 corrupted batches behind it (5 for an LLM); with less, the provisional step stays. Manual overrides: none.

**What the choices add up to.** Clean batches with any alert: **10/10 before** the batch alerting layer, **5/10 after** it (50.0% [23.7-76.3] (5/10)); alerts per clean batch 3.1 -> 0.5. The highest row false-alarm rate on clean rows is 0.06% (i), within the 0.2% cap, and the row layer is identical before and after. The clean-batch alerts that remain come from: l 5/10 (critical: alerts on every flag). On real, unsanitised batches (which carry real issues): 10/10 alerted. Row-level detection (recall) is unchanged by construction: the alerting layer reads the row flags and never edits them. At the benchmark's 2% injection rate, no single-problem injected batch lost its alert; in mixed batches, j lost one. Held back: j in mixed batch 4 (c+j+k): 29 injected rows, 29 flagged, threshold 47. In a mixed batch a type gets only the rows no earlier type took, so it can carry far fewer than 2% of the rows; every injected row was still flagged. The thresholds do cost detection when a corruption touches fewer rows than the threshold: a batch then alerts only if false flags make up the difference. Measured in the alert sweep: f at 0.1% (5 injected rows per batch, threshold 3): 5/5 -> 4/5; i at 0.1% (5 injected rows per batch, threshold 13): 5/5 -> 0/5; j at 0.1% (5 injected rows per batch, threshold 47): 5/5 -> 0/5; j at 0.5% (25 injected rows per batch, threshold 47): 5/5 -> 0/5; k at 0.1% (5 injected rows per batch, threshold 7): 5/5 -> 3/5. Those rows are still flagged on the rows themselves; only the batch alert is held back.

**Auditability in practice.**
- Every rule and statistical alert carries a check id, the columns, example rows, and the observed
  vs expected value.
- Every LLM verdict is stored with its prompt, answer, tokens and latency in
  `project_b/llm_cache/`, so an auditor can replay and read it. The cache makes the LLM
  reproducible, not deterministic: a fresh call can answer differently, which is why the LLM only
  ever confirms flags a deterministic check raised.
- Personal data (l) always alerts at once, however few rows. The price is accepted: a new 311
  category label can raise a PII alert until the reference vocabulary is refreshed. Ignoring
  capitalisation in category labels would stop that, but would also hide a name written into a
  label, so it was not adopted (RESULTS_B.md section 7).
- An LLM reply that cannot be read is an abstention, never a "clean" verdict. In the pipeline a
  value the LLM did not judge keeps its cheap flag, so an unreadable reply can never silence an
  alert.
