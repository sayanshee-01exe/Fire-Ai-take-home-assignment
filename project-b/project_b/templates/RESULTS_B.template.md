## 1. Setup

**Data.** {{data}} The download keeps every value exactly as delivered (all strings; only empty
fields become null), so placeholders such as `N/A` survive for profiling. The detectors see a typed
"feed": `unique_key` integer, coordinates floats, everything else strings. Dates stay ISO strings
because a real JSON/CSV feed delivers them as text, which is what makes a date-format switch possible.

**Split and batches.** Nothing is fitted, calibrated or chosen on evaluation data.

{{settings}}

**Clean pool.** Batches are cut from a sanitised pool. `project_b/data/clean.py` removes rows that
already carry one of the injected problems, so a detector that flags a real pre-existing issue is
not charged with a false alarm. The same code runs in the profiler and in the benchmark.

{{sanitizer}}

**How detection is scored.**
- Row-level problems: recall over the injected rows; row FPR = flagged share of the rows in clean
  batches; precision at the 2 % injection rate.
- Batch-level problems: share of corrupted batches alerted vs share of clean batches alerted, plus
  whether the alert names the right column or agency.
- Every rate carries its Wilson 95 % interval and k/n.
- An error on a corrupted batch counts as a miss. On a clean batch it is left out of the
  false-alarm rate (an error is not a correct "no alarm"), but an alert raised anyway still counts.
- An LLM that cannot be reached is reported as "not run", never as zero.
- **A row the LLM gave no readable verdict for is an abstention, never a clean row.** That covers a
  reply cut off at the output limit, a reply blocked by a filter, or a reply that skips the row. The
  LLM rates in the detector tables are *conditional on a readable verdict*. The coverage table
  reports how often a verdict came back, and the *overall operational* rates count every
  abstention as "no alert" (a miss on an injected row, no false alarm on a clean one).

**Cost and speed.**
- Rule and statistical detectors are charged single-core CPU time at
  `config.COMPUTE_USD_PER_VCPU_HOUR`.
- LLM detectors are charged their measured tokens at the list price of the model.
- Throughput is measured on this laptop.
- Explanation clarity is a 0-5 rubric: names the check, localises it, shows the observed value,
  shows the expected value, reproducible. LLM explanations are also checked for grounding: does the
  quoted value really appear in the row?

**Reproducibility.**
- Every random draw is seeded from `config.SEED`.
- Every Gemini answer is appended to `project_b/llm_cache/<model>.jsonl` with its tokens and
  latency. With `LLM_MODE=replay` a re-run uses only that cache, so accuracy, cost and latency
  reproduce without an API key.
- Within one live run a prompt is sent at most once, so the replay equals the run.

## 3. Task 2 - corruption injector

`project_b/inject.py` injects each of the 12 problem types into clean batches at a controlled
rate. It records exactly which rows and columns it changed (the ground truth), and a seed fixes
every choice.

{{injection}}

**Keeping the ground truth honest.** The injector and the detectors were written independently
against `project_b/DESIGN.md`, like a red team and a blue team, so detectors cannot exploit
injector artefacts. An implementation audit then removed four artefacts that made one family look
better or worse for the wrong reason:

- **Problem j (descriptor mismatch).** Catch-all descriptors such as "Other", "N/A" and
  "Other (complaint details)" are never used as a mismatch: they contradict nothing.
- **Problem f (near-duplicates).** A copy whose address was mistyped is moved 5-15 m, as a
  re-geocoded address would be. Its latitude/longitude are recomputed from its new state-plane
  x/y with the NYC projection (EPSG:2263), so it obeys the same exact relation as real rows.
- **Problem k (resolution text contradicting status).** Contradictions use only texts of the row's
  own agency, chosen evenly, and both text screens below apply.
- **Unread texts.** A warning fires if a new data snapshot contains candidate texts nobody has read.

**Resolution text screens (problem k).** A text that is at least 95 % associated with one status
group is a contradiction only if its words say so. The criteria were written down before any text
was read:
- An **open** text is kept only if it says the request is not finished: under review or
  investigation, scheduled, assigned, the agency will visit or contact, a work order with a future
  date, or waiting for a form.
- A **closed** text is kept only if it says the agency's handling is finished: action taken or the
  condition fixed, an inspection or response completed with an outcome, or the complaint
  explicitly closed.
- Status pointers, instructions such as "call 311", acknowledgements, referrals, duplicates of a
  still-open request, failed or no-access visits, future steps and ambiguous texts are excluded.
  Excluding is the safe direction: an excluded text never carries an injected contradiction, while
  the legitimate records holding it stay in the data untouched.

Only texts that qualify on January-August data are candidates, so the screen never needed
evaluation data. Every candidate was read, and an independent reviewer re-read all of them and
agreed with every decision. That review was not fully blind: the reviewer had seen the exclusion
list first. The decisions are in `tests/data/k_screen_decisions.json`, and a test checks the code
against each of them.

{{k_screen}}

The screens only narrow which rows may carry a contradiction. `tests/test_inject.py` checks for
every problem and variant that the injector still makes the requested number of corruptions, and
that the labelled rows are exactly the rows that changed.

## 5. Task 5 - hybrid pipeline

`project_b/pipeline.py` has one step per problem:
- **Cheap checks first.** One or more rule/statistical detectors run on every row, and their flags
  are OR-ed.
- **LLM as a confirmer only.** Where the evidence supports it, an LLM must confirm a flag before it
  alerts. It can veto false alarms but never adds detections.
- **One call per distinct value.** The LLM judges each distinct flagged value once (311 values are
  templated), within a per-batch cap. A value it cannot judge keeps its cheap flag.
- **Quarantine.** A broken schema or date format quarantines the whole batch.
- **Mixed-batch evaluation.** The pipeline is evaluated on the benchmark's own single-problem
  batches, on clean batches, on real unsanitised batches, and on mixed batches carrying three
  corruption types at once. In a mixed batch each type is injected on its own rows, and a copy of a
  corrupted row inherits its label, so every label stays exact.

**How each step is chosen.** {{plan_rule}}

{{pipeline}}

### 5a. Batch alerting layer

**Why.** Before this layer, every check alerted on any flagged row, and the first pipeline
evaluation raised an alert on every clean batch. Row false-alarm rates of a few in 10,000 still
fire on most 5,000-row batches. That result motivated the layer. The rule below was written
down (DESIGN.md section 7a) before any threshold was computed, and nothing in it was tuned on
September-December data.

**The final alerting policy.**
- **Two layers.** The row layer is unchanged: the same detectors, the same flagged rows, the same
  row false-alarm rates. A separate batch alerting layer decides whether a check raises a batch
  alert.
- **Critical checks alert on every flag:**
  - schema, type and date-format breaks (a, b, c), which also quarantine the batch;
  - personal data in free text (l);
  - the null-spike statistic (g), which is already calibrated per batch.
- **Every other row check (d, e, f, h, i, j, k)** alerts only when a batch has at least its
  threshold of flagged rows. An alert raised without row flags (a structural finding) passes at once.

**How the thresholds were calibrated (January-August only).**
- Detectors were fitted on the clean pool from January to June.
- The rows each check flags were counted on every clean 5,000-row batch from July and August.
  These batches are held out from that fit but still inside the reference period.
- A check's threshold is the smallest count k such that at most 5 % of those calibration batches
  have k or more flagged rows. This is the rule and the target (`config.TARGET_BATCH_FAR`) that the
  project's batch-level statistical detectors already use, so no new number was introduced.
- LLM confirmation was off during calibration, so no Gemini call was made.
- September-December was read only afterwards, to measure the result. Every pipeline record holds
  both verdicts, "before" (every flag alerts) and "after", so the comparison below comes from one run.

## 6. Task 6 - scale design: 50 million rows a day across 120 customers

The table below separates **measured** figures (from this repository's runs), **assumptions**
(constants in `project_b/scale.py`, each a stated judgement) and **projections** (arithmetic on
the two). A figure that needs a measurement not yet taken is shown as pending.

{{scale}}

**Architecture at that scale.**
- **Streaming tier, every row.** The schema/date gate and the row rules run as vectorised workers
  on arriving batches; they are stateless and scale out horizontally.
- **Batch tier, per customer.** Statistical detectors keep per-customer baselines (null rates per
  agency, value-pair frequencies, text vocabularies) in a small state store. Baselines are
  refreshed nightly, only from batches that passed, so a corruption cannot teach itself to the
  baseline.
- **Escalation tier.** Flagged distinct values go to an asynchronous LLM queue with a per-customer
  daily budget. Verdicts are cached per customer and value, so cost follows the number of new
  values, not the number of rows. Alerts that wait for the LLM are shown as "pending review" and
  never block a dashboard refresh.
- **Cross-batch duplicate state.** Problems e and f need memory across batches: a keyed store or a
  Bloom filter per customer with a time-to-live, replacing the per-batch reset used in the
  benchmark.

**Customer-specific schemas.**
- 120 customers will not share NYC 311's column names. Each customer gets a versioned data
  contract that maps its columns to canonical meanings (timestamp, category, sub-category,
  location, free text, status).
- An LLM may *propose* that mapping once, at onboarding (the "compiled" use of an LLM: offline,
  reviewed by a person, then frozen). Every row check then runs against the contract without an LLM.
- Rules are written against canonical meanings, so they carry over between customers.
- Statistical baselines and lookup tables (allow-lists, text screens) are per customer. A new
  customer starts with pooled priors until it has enough history.

**What changes at scale, and why.**
- **The LLM moves out of the row path.** Per-row LLM review that is affordable on a sample is
  linear in rows. Only escalation of distinct, already-flagged values survives at 50 M rows a day.
- **Personal data stays inside.** Free text that may contain personal data should not be sent to
  an external model without a data-processing agreement. At scale the regex and the local novelty
  score run first, text is redacted before any LLM call, or a self-hosted model is used.
- **Alert fatigue becomes the binding constraint.** 120 customers x 12 checks x thousands of
  batches a day need per-check false-alarm budgets, de-duplicated incidents and severity routing.
  This is why the plan rule caps false alarms before it looks at detection. It is also why the
  batch alerting layer (section 5a) exists: its thresholds would be calibrated per customer, on a
  rolling window that matches how that customer's detectors are refitted.
- **The injector becomes a production canary.** Small synthetic corruptions injected into a copy of
  live traffic measure every check's detection rate continuously, per customer.

## 7. Limitations and disclosures

- **Some choices were first made with evaluation data on screen.** An implementation audit found
  three such cases: the hand-set null-rate limits of the null-spike rule, the near-duplicate
  similarity weights, and the descriptor classifier's model. Each was re-checked on
  January-August data alone, under a selection rule written before the re-check. January-August
  data supports the same values in all three cases, but the history is disclosed here.
- **Clean-batch false alarms of some rules are near zero partly by construction.** Where the
  sanitiser removes exactly what a rule checks (coordinates outside NYC, exact duplicates), the
  rule cannot false-alarm on the clean pool. The real-data background table shows the alerts such
  a rule raises on unsanitised data.
- **LLM samples are enriched.** About half the rows in an LLM review prompt are corrupted, far more
  than the 2 % in real traffic. Precision is re-weighted to the injection rate; recall is not.
- **Determinism is measured on one batch per LLM detector.** For batch-level problems that is a
  single verdict. Rows a repeat abstained on are left out of the comparison.
- **Some Gemini replies were unreadable and were not retried.** Section 4 lists each one with its
  cause: replies that looped until they hit the output-token limit, and a reply blocked by the
  recitation filter. Their rows are abstentions. A retry with smaller prompts or a higher output limit could recover verdicts,
  but would cost new requests and could loop again. Coverage is reported instead, so a reader can
  see how much the LLM did not judge.
- **The text screens are human judgements** about one data snapshot. 30 closed texts were kept but
  judged borderline (listed in section 3).
- **The alert thresholds assume Sep-Dec looks like Jul-Aug.** They were calibrated on summer
  batches; a seasonal shift in false flags would move the real alert rate away from the 5 % target
  per check. Per-customer, rolling recalibration is the production answer (section 6).
- **The need for an alerting layer was found on evaluation data.** The rule and its target were
  then taken from the existing design, written down before calibration, and not adjusted after the
  evaluation result.
- **New 311 category labels still raise PII alerts.** The novelty statistic counts a never-seen
  capitalised word as name-shaped, and every word of a new Title Case label is capitalised
  ("Allowed in Smoke Free Area", first seen December 2023). These are the PII alerts that remain on
  clean batches (section 5a); every one examined was a false positive. Ignoring capitalisation in
  category labels would remove them, but was deliberately not adopted: a personal name inside such
  a label would then go unflagged, the benchmark cannot measure that risk, and PII alerts must stay
  immediate. Three narrower fixes were adopted, each decided on January-August data alone
  (DESIGN.md section 4, l): a cue word inside a Title Case label is no cue; public and toll-free
  numbers from the explicit allow-lists are not novel; one public federal number joined the
  allow-list. Refreshing the reference vocabulary on accepted batches is the production remedy.
- **A mistyped house-number digit now counts as a different building.** The near-duplicate
  checks treat two addresses with different building numbers as different requests, so that
  distinct reports along one street that share a block-level geocode are not merged. A re-entered
  request whose building number was mistyped is therefore not caught (DESIGN.md section 4, f;
  measured on January-August data only).
- **The clean pool keeps a few real near-duplicates.** The sanitiser's near-duplicate key
  normalises only STREET and AVENUE. A pair spelled PARKWAY / PKW, for example, stays in the pool,
  and a detector that finds it is charged with a false alarm. The sanitiser was left unchanged so
  that the dataset and every label stay as they were.
- **The unit-test fixture batch is from 16 October 2023** (evaluation period). It is used for
  regression tests, not tuning; any future retuning against those tests would be tuning on
  evaluation data.
- **Free-tier limits come from the AI Studio rate-limit page** (15 requests/min, 250,000
  tokens/min, 500 requests/day for the model used, read on 2026-11-21), not from an API. The run
  never relies on them: a quota error stops further LLM calls, and a rerun resumes from the cache.

## 8. How to reproduce

The raw snapshot is described in `dataset_manifest.json`: source query, download time, file size,
row count, schema and SHA-256. Every run verifies the file against it and stops if the file is
missing or different. README.md ("Dataset snapshot") says how to get the exact file.

```
python -m pip install -r requirements.txt
python -m project_b                    # every step; replays cached Gemini answers when no key is set
python -m project_b --steps report     # only re-render RESULTS_B.md and DECISION_MATRIX.md
python -m pytest tests -q
```
